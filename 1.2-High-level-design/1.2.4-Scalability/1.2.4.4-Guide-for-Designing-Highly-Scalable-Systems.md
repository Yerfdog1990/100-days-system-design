## 1. Overview

**Highly scalable systems** handle growing **users, data and workload** efficiently. Building them takes **deliberate architectural planning** and an understanding of scalability principles, so applications stay **reliable and fast** as demand grows.

- Handle more users and traffic **without a major redesign**: growth is smooth.
- Keep **fast response times** and stay **stable and available** during heavy load or spikes.

**Example:** a streaming platform like **Netflix** adds servers and uses load balancing so millions of people can watch at once. But overall performance still depends on **database efficiency, overall design and bottlenecks**, not just server count.

> 💡 **Key idea:** scalability is **designed in**, not bolted on. Principles (decomposition, statelessness, loose coupling) make scaling *possible*; patterns and techniques (load balancing, caching, sharding, queues, auto scaling) make it *happen*; operations (monitoring, testing, capacity planning) keep it *working*.

## 2. Real-World Examples of Highly Scalable Systems

| System | How it scales |
|---|---|
| **Amazon Web Services (AWS)** | Scalable compute, storage, databases and networking; a global footprint of **Regions and Availability Zones** supports highly available, scalable apps. |
| **Google Search** | Massive **distributed infrastructure**, heavy **caching** and **distributed data processing** to answer queries fast. |
| **Netflix** | **Service-oriented / microservices** on cloud infrastructure; components **scale independently** with demand. |
| **Uber** | **Distributed systems** and **real-time processing** for rider–driver matching, pricing and trip management at global volume (the source article cites 75 billion trips worldwide as of May 2026). |
| **Meta (Facebook)** | Globally distributed infrastructure and large-scale data systems serving **billions** of people across its apps. |

## 3. Why Scalability Matters

- Handles growing workload and user demand **without significant performance loss**.
- Lets systems grow by **scaling up** (more CPU/RAM/storage) or **scaling out** (more servers). *(See [1.2.4.2](1.2.4.2-Horizontal-and-Vertical-Scaling.md).)*
- Keeps **acceptable performance** and **efficient resource use** as load grows.

> ⚠️ **Scalability ≠ high availability.** Staying *up* also needs **redundancy, replication and failover**. A system can handle huge load and still go down if one critical component fails.

---

## 4. Factors Affecting Scalability

| Factor | Why it matters |
|---|---|
| **Architecture** | The system's structure decides how easily it can grow (monolith vs services, stateful vs stateless). |
| **Resource allocation** | CPU, memory and storage must be allocated to match the workload: not starved, not wasted. |
| **Load balancing** | Spreading requests evenly stops any single component from being overloaded. |
| **Data management** | **Sharding and replication** prevent the database from becoming the bottleneck. |
| **Parallelism** | Parallel processing and concurrency let the system do **many tasks at once**. |

## 5. Design Principles for Scalable Systems

| Principle | Meaning | In practice |
|---|---|---|
| **Decomposition** | Break the system into **smaller components/services** | Scale or change one part without touching the rest |
| **Loose coupling** | **Minimal dependencies** between components | Talk through APIs/events; one service's change or failure doesn't ripple everywhere |
| **Service-Oriented Architecture (SOA)** | Functionality organised into **services with well-defined interfaces** | Teams develop, deploy and scale services independently |
| **Horizontal scalability** | Scale by **adding instances** rather than upgrading one machine | No hardware ceiling; better resource use and resilience |
| **Statelessness** | **Minimise server-side state** | Any request can go to any instance; sessions live in a shared store or token |
| **Caching** | Keep frequently used data/results in fast storage | Fewer repeated computations and DB hits; lower latency |
| **Fault tolerance** | Expect failures; use **redundancy, replication, failover** | One instance or zone failing doesn't take the service down |

```
 Decomposition ─► Loose coupling ─► Stateless services ─► Horizontal scaling ─► + Cache ─► + Fault tolerance
 (split it)       (separate it)     (any instance works)  (add instances)      (less load)  (survive failures)
```

## 6. Architectural Patterns for Scalability

Reusable solutions that help a system grow:

### 6.1 Microservices architecture

Small, **independent services**, each owning one business function.

- **Independently deployable**; each handles a specific feature.
- **Scaled independently** by demand.
- Changes in one service **don't affect others**.

*(Deep dive: [1.2.3.2 Microservices](../1.2.3-System-architecture/1.2.3.2-Microservices.md).)*

### 6.2 Event-driven architecture

Components communicate through **events** (state changes or important actions).

- **Events instead of direct calls**, so less coupling.
- **Asynchronous** communication.
- **Absorbs sudden workload increases**: events wait in the broker until consumers catch up.

*(Deep dive: [1.2.3.4 EDA](../1.2.3-System-architecture/1.2.3.4-Event-Driven-Architecture.md).)*

### 6.3 Distributed systems

Spread **computation and data** across many machines.

- Many servers **work together** on tasks.
- Data is distributed with **sharding, replication and partitioning**.
- Avoids **single-machine bottlenecks**.

### 6.4 CQRS (Command Query Responsibility Segregation)

**Separate** the parts that **change data** (commands) from the parts that **read data** (queries), so each can be **designed and scaled independently**.

```
                  ┌── Commands (create/update/delete) ──► Write model ──► Write DB
  Client ─────────┤                                                          │
                  │                                              events / replication
                  │                                                          ▼
                  └── Queries (read) ──────────────────► Read model ◄── Read DB(s) / search index
                                                     (scaled out: many replicas)
```

- Useful when **reads and writes differ a lot** (e.g. 100 reads per write).
- ⚠️ Adds **complexity** and usually **eventual consistency** between the write and read sides. Use it only when the workloads truly differ.

### 6.5 Database sharding

Split a large database into **smaller parts (shards)** on different servers.

```
                 shard key = user_id
                        │
       ┌────────────────┼────────────────┐
       ▼                ▼                ▼
  Shard 1          Shard 2           Shard 3
  users 1–1M       users 1M–2M       users 2M–3M     ← each shard holds part of the data
```

- Data is split by a **shard key**.
- Each shard manages **a portion** of the data.
- Spreads **database load** (especially writes) and storage.

### 6.6 Load balancing

Distributes incoming requests across servers.

- Prevents **overload** on any one server.
- Algorithms like **round robin** or **least connections**.
- Makes **horizontal scaling** usable.

## 7. Techniques for Horizontal Scaling

| Technique | How it helps |
|---|---|
| **Load balancing** | Spreads requests across instances so no component becomes a bottleneck |
| **Caching** (application + infrastructure, e.g. Redis, CDN) | Serves frequently used data from fast storage, which cuts backend load dramatically |
| **Partitioning / sharding** | Splits data and computation across nodes so parts scale independently |
| **Asynchronous processing** (message queues, streaming platforms) | Separates **accepting** a request from **doing** the heavy work; absorbs spikes |
| **Auto scaling** | Adds/removes resources automatically based on metrics (CPU, queue length, requests) |

### All together: a reference architecture

```
                          ┌──────── CDN (static assets, video) ◄────────┐
                          │                                             │
 Users ─► DNS ─► Load Balancer ─► [App] [App] [App] … (stateless, auto-scaled)   Users
                                     │        │
              ┌──────────────────────┼────────┼──────────────────────┐
              ▼                      ▼        ▼                      ▼
        Cache (Redis)        Write DB (sharded)   Read replicas     Message queue / stream
                                     │                                 │
                                     └── replication ──►               ▼
                                                               Workers (auto-scaled):
                                                               emails, video encoding,
                                                               search indexing, analytics
        Monitoring · logging · tracing · alerting across everything
```

## 8. Operational Best Practices

Design gets you started; **operations keep it scaling in production**.

| Practice | What it means |
|---|---|
| **Automation** | Automate provisioning, deployment and configuration (CI/CD, infrastructure-as-code). |
| **Monitoring & alerting** | Track latency, errors, throughput and utilization; **alert** before users notice. |
| **Scalability testing** | Regular load and stress tests to find bottlenecks **before** they cause outages. *(See [1.2.4.3 §5](1.2.4.3-Choosing-the-Right-Scalability-Approach.md#5-testing-your-apps-scalability).)* |
| **Horizontal scaling** | Design so you can add resources and **spread load evenly**. |
| **Fault tolerance & resilience** | **Redundancy and failover** keep the system available when parts fail. |
| **Capacity planning** | Watch usage trends and **plan future capacity** ahead of demand. |
| **Security & compliance** | Strong security controls and compliance with regulations, at every scale. |
| **Disaster recovery** | **Backups, redundancy, failover clustering**, multi-region recovery plans, so the system can recover from major failures. |

## 9. Challenges in Achieving High Scalability

| Challenge | Detail | Common mitigation |
|---|---|---|
| **Concurrency & synchronization** | Many processes touching shared resources → **race conditions, deadlocks**, data-integrity issues | Minimise shared state; optimistic locking; idempotent operations; queues |
| **Data partitioning & sharding** | Need **balanced** data distribution, no **hotspots**, good performance | Good shard keys, consistent hashing, rebalancing tools |
| **Consistency, availability, partition tolerance (CAP)** | When a **network partition** happens, a distributed system must **trade off consistency vs availability** | Choose per use case: strong consistency (payments) vs high availability (feeds) |
| **Scalability testing & optimization** | Realistic workloads, finding bottlenecks, the right tools | Production-like test environments, profiling, observability |
| **Cost & resource management** | More infrastructure = more cost | Auto scaling, right-sizing, capacity planning, cost monitoring |

### CAP in one picture

```
   Network partition splits the cluster:    Node A  ✕───✕  Node B

   Option 1 (favour CONSISTENCY):  refuse some requests until nodes can agree  → may be unavailable
   Option 2 (favour AVAILABILITY): keep answering on both sides                → answers may be stale/conflicting
```

> 💡 Partitions **will** happen in distributed systems, so the real choice during one is **consistency vs availability**. *(Covered in depth later in the course: Reliability & CAP Theorem.)*

## 10. Design Checklist

A quick checklist to use when designing (or in an interview):

| ✔ | Question |
|---|---|
| ☐ | What's the expected **load and growth** (users, requests/s, data size)? |
| ☐ | Is the system **decomposed** into loosely coupled parts? |
| ☐ | Are app servers **stateless** (sessions in a shared store/token)? |
| ☐ | Is there a **load balancer** with health checks, and **auto scaling**? |
| ☐ | What's **cached** (app cache, CDN)? How is it invalidated? |
| ☐ | How does the **database** scale: replicas for reads, sharding for writes, CQRS if needed? |
| ☐ | Which work can be **asynchronous** (queues/events)? |
| ☐ | Where are the **single points of failure**, and what's the **failover**? |
| ☐ | What's the **consistency** requirement per feature? |
| ☐ | How is it **monitored, tested and capacity-planned**? Is there a **disaster-recovery** plan? |

## 11. Quick Revision

- **Highly scalable** = handles growing users/data/workload with **stable performance** and **without redesign**. Availability additionally needs **redundancy and failover**.
- **Examples:** AWS (Regions/AZs), Google Search (distributed + caching), Netflix (services), Uber (real-time distributed), Meta (global infra).
- **Factors:** architecture · resource allocation · load balancing · data management (sharding/replication) · parallelism.
- **Principles:** **decomposition** · loose coupling · SOA · horizontal scalability · **statelessness** · caching · fault tolerance.
- **Patterns:** microservices · event-driven · distributed systems · **CQRS** (separate read/write) · **sharding** (shard key) · load balancing.
- **Horizontal techniques:** load balancing · caching · partitioning/sharding · **async processing** · **auto scaling**.
- **Operations:** automation · monitoring/alerting · scalability testing · fault tolerance · capacity planning · security · disaster recovery.
- **Challenges:** concurrency (races, deadlocks) · partitioning (hotspots) · **CAP trade-off** · testing · cost.

## 12. Self-Check Quiz: Interview Q&A

> ⭐ These questions come from the GeeksforGeeks suggested quiz and are **important for system design interviews**. (The source repeats the "decomposition" question twice, so it appears once here.) Try each one before opening the answer.

### Q1. Why are highly scalable systems important in modern application design?

- A. They allow systems to handle increasing users and workloads without performance degradation
- B. They eliminate the need for databases in applications
- C. They restrict the number of users accessing the system
- D. They remove the need for monitoring and maintenance

<details>
<summary>Answer</summary>

**A. They allow systems to handle increasing users and workloads without performance degradation**

Scalable systems handle growing traffic, users and data while keeping performance, availability and reliability. *(D is false: scalable systems need **more** monitoring, not less.)* See [§3](#3-why-scalability-matters).
</details>

### Q2. Which design principle helps systems scale by dividing them into smaller independent components?

- A. Decomposition
- B. Centralized processing
- C. Single-server architecture
- D. Static resource allocation

<details>
<summary>Answer</summary>

**A. Decomposition**

Breaking a large system into smaller services/components lets each be developed, deployed and **scaled independently**. See [§5](#5-design-principles-for-scalable-systems).
</details>

### Q3. Why are stateless services preferred in scalable architectures?

- A. They allow requests to be handled by any server instance
- B. They store all session data in a single machine
- C. They remove the need for load balancers
- D. They eliminate database usage

<details>
<summary>Answer</summary>

**A. They allow requests to be handled by any server instance**

No session data lives on the server, so requests can be spread across many servers easily. *(They still need load balancers and databases.)* See [1.2.3.7](../1.2.3-System-architecture/1.2.3.7-Stateless-and-Stateful-Systems.md).
</details>

### Q4. How does caching help improve scalability in distributed systems?

- A. By storing frequently accessed data to reduce backend load
- B. By increasing database size automatically
- C. By limiting the number of user requests
- D. By removing network communication

<details>
<summary>Answer</summary>

**A. By storing frequently accessed data to reduce backend load**

Fewer repeated database queries and computations mean faster responses and less pressure on backend services. See [§7](#7-techniques-for-horizontal-scaling).
</details>

### Q5. What is the main purpose of load balancing in scalable architectures?

- A. To distribute incoming requests across multiple servers
- B. To replace the need for distributed database
- C. To store user session data permanently
- D. To eliminate network latency completely

<details>
<summary>Answer</summary>

**A. To distribute incoming requests across multiple servers**

Even distribution prevents overload and improves availability (failed servers are skipped). See [§6.6](#66-load-balancing).
</details>

### Q6. What is one major challenge when building highly scalable distributed systems?

- A. Managing data consistency and communication across distributed components
- B. Eliminating the need for monitoring tools
- C. Avoiding the use of databases entirely
- D. Removing concurrency from applications

<details>
<summary>Answer</summary>

**A. Managing data consistency and communication across distributed components**

Distribution brings consistency trade-offs (CAP), network delays and coordination problems between components. See [§9](#9-challenges-in-achieving-high-scalability).
</details>

### Bonus Questions

> Extra practice on the rest of the topic.

### B1. What is CQRS, and when is it worth using?

<details>
<summary>Answer</summary>

**Command Query Responsibility Segregation**: separate models/paths for **writes** (commands) and **reads** (queries), so each can be designed and scaled independently. Worth it when read and write workloads **differ a lot**. It adds complexity and usually eventual consistency.
</details>

### B2. What is a shard key, and what makes a bad one?

<details>
<summary>Answer</summary>

The field used to decide **which shard** stores each record (e.g. `user_id`). A bad key creates **hotspots** (e.g. sharding by country when most users are in one country), causing **uneven load**.
</details>

### B3. How does asynchronous processing improve scalability?

<details>
<summary>Answer</summary>

The request handler just **accepts** the work and puts it on a **queue/stream**; workers do the heavy part later and scale independently. Responses stay fast, and spikes are buffered instead of overwhelming the system.
</details>

### B4. During a network partition, what trade-off must a distributed system make?

<details>
<summary>Answer</summary>

Between **consistency** (refuse requests that might return stale or conflicting data) and **availability** (keep answering, possibly with stale data). This is the CAP theorem.
</details>

### B5. What are race conditions and deadlocks?

<details>
<summary>Answer</summary>

A **race condition** is when the result depends on the timing of concurrent operations (e.g. two requests both reading stock = 1 and both selling it). A **deadlock** is when two processes each wait for a resource the other holds, so neither can proceed.
</details>

### B6. Why is capacity planning still needed if you have auto scaling?

<details>
<summary>Answer</summary>

Auto scaling works **within limits** (account quotas, max instance counts, database capacity, budget). Capacity planning makes sure those limits, the database and other shared parts can handle **future** growth before it arrives.
</details>
