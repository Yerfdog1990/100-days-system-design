## 1. What is a Bottleneck?

A **bottleneck** is the point in a system where **data flow or processing gets restricted**, reducing overall performance. It happens when **one component is slower than the rest** and can't keep up with incoming requests, causing **lower throughput, scalability problems and delays** as load grows.

- Bottlenecks usually **show up at peak load**: everything looks fine with few users.
- They can be in **databases, networks, servers, code, storage, authentication or third-party services**.
- **Fixing one bottleneck often exposes the next one.**

**Example:** a web app has a **fast server but a slow database**. When many users arrive, the **database** can't process queries fast enough, so it's the bottleneck, and the fast server just waits.

```
   Like the neck of a bottle: the narrowest part limits the whole flow

   Requests ════════════► [ LB ] ══════► [ App servers ] ═══► [DB] ═══► responses
   10,000/s                10,000/s          10,000/s        2,000/s
                                                               ▲
                                                 bottleneck: the whole system
                                                 can only do ~2,000 req/s
```

> 💡 **Key rule:** a system's capacity equals its **slowest stage's** capacity. Scaling anything *other* than the bottleneck adds cost but **no throughput**.

```
 Fix the DB (add cache + replicas) → now 8,000/s → the APP servers become the limit → scale them → …
 "Whack-a-mole": measure → fix the narrowest point → measure again
```

## 2. Types of Bottlenecks at a Glance

| # | Type | Typical cause | Typical fix |
|---|---|---|---|
| 1 | **Database** | Slow queries, missing indexes, locks, too many connections | Indexes, query tuning, caching, replicas, sharding, connection pooling |
| 2 | **Network** | Limited bandwidth, high latency, packet loss, congestion | CDN, compression, fewer round trips, co-location, more bandwidth |
| 3 | **Server** | Not enough CPU, RAM or disk I/O for concurrent requests | Scale out/up, async processing, offload heavy work |
| 4 | **Authentication** | Login surges, slow hashing/verification, central auth service | Token-based auth (JWT), caching, scaling the auth service |
| 5 | **Third-party services** | External latency, downtime, rate limits, API changes | Timeouts, retries, circuit breakers, caching, fallbacks, async |
| 6 | **Code execution** | Inefficient algorithms, excess CPU, lock contention | Profiling, better algorithms, less synchronization |
| 7 | **Data storage** | Low disk I/O / throughput, high latency, capacity limits | Faster disks (SSD/NVMe), object storage, distributing data |

## 3. Database Bottlenecks

Database operations **limit the whole application**: from inefficient queries, **missing indexes**, **lock contention**, too many **connections**, or limited DB resources.

- **Slow queries** increase response times and lower how many requests the DB can handle.
- **Poor indexing** or bad query patterns force the DB to **scan far more data** than needed.
- High **CPU, memory or connection** usage limits it further.

**Example:** during a **sale**, an e-commerce site gets a flood of orders; inefficient product/order queries slow the DB, and every request waits.

**Why so common?** Nearly every request touches the database, and it's usually **stateful and hard to scale out** (see [1.2.4.2 §6](1.2.4.2-Horizontal-and-Vertical-Scaling.md#6-scaling-each-tier-of-a-system)).

**Two classic causes:**

```sql
-- 1) Missing index: full table scan on 50M rows
SELECT * FROM orders WHERE customer_id = 42;        -- slow without an index
CREATE INDEX idx_orders_customer ON orders(customer_id);  -- now a fast index lookup
```

```
-- 2) The N+1 query problem (common with ORMs)
SELECT * FROM orders WHERE customer_id = 42;   -- 1 query → 100 orders
SELECT * FROM items WHERE order_id = 1;        -- +100 queries, one per order
SELECT * FROM items WHERE order_id = 2;
...                                            ⇒ 101 round trips instead of 1–2
Fix: one JOIN, or SELECT … WHERE order_id IN (…), or eager loading in the ORM
```

| Fix | Helps with |
|---|---|
| **Indexes** & query tuning (`EXPLAIN`) | Slow scans |
| **Caching** (Redis) | Repeated reads |
| **Read replicas** | Read-heavy load |
| **Connection pooling** | Too many connections |
| **Sharding / partitioning** | Write volume and data size |
| **Shorter transactions, better locking** | Lock contention |

## 4. Network Bottlenecks

Something in the network **limits capacity or performance**, slowing the whole system. Can occur anywhere in the network topology.

- Causes: **bandwidth limits, high latency, packet loss, congestion, inefficient topology**.
- Distributed systems are especially sensitive: services talk to each other constantly.

**Example:** a video streaming service **without enough content-delivery infrastructure**. When too many users stream at once, the network is strained, and viewers see **buffering and low quality**.

| Fix | How |
|---|---|
| **CDN** | Serve content from edge servers near users |
| **Compression** | gzip/brotli for text; efficient video codecs |
| **Fewer round trips** | Batch requests, avoid "chatty" APIs, use HTTP/2 or HTTP/3 |
| **Co-location** | Put services that talk a lot in the same region/zone |
| **Efficient payloads** | Send only needed fields; binary formats (Protobuf) for internal traffic |
| **More bandwidth / better topology** | Upgrade links, remove congested hops |

## 5. Server Bottlenecks

The **application server can't handle more requests or concurrent connections**, because of limited **CPU, RAM or disk I/O**.

- A **viral post** on a social site sends a huge surge of users at once; an under-resourced server becomes **unresponsive**.
- **Example:** an image-upload app grows, and its **CPU-heavy image-processing algorithm** maxes out the CPU, so processing is delayed and the whole app feels sluggish.

| Fix | How |
|---|---|
| **Scale out** | More instances behind a load balancer + **auto scaling** |
| **Scale up** | Bigger instance for a quick fix |
| **Offload heavy work** | Move image processing to a **queue + worker pool** (async) |
| **Cache responses** | Don't recompute the same results |
| **Tune the runtime** | Thread pools, connection limits, memory settings |

```
 Before:  Upload ─► App server (resize image… 4 s, CPU 100%) ─► response      ❌ everyone waits

 After:   Upload ─► App server ─► store file + enqueue job ─► "processing…" (fast)  ✅
                                       └──► Workers (auto-scaled) resize images
```

## 6. Authentication Bottlenecks

Verifying identity becomes **slow or overloaded**, so every request (or login) waits.

- Caused by **high volumes of login requests** or **inefficient authentication mechanisms**.
- Also by **limited infrastructure** or poorly optimized auth workflows.

**Example:** an **e-banking app at peak times** (e.g. salary day). The auth system can't keep up and logins are delayed.

**Why it happens:** password hashing (bcrypt/argon2) is **deliberately CPU-expensive**; a **central auth service or session DB** checked on **every** request becomes a hotspot.

| Fix | How |
|---|---|
| **Token-based auth (JWT)** | Services verify a signed token **locally** instead of calling the auth service each time |
| **Cache sessions/permissions** | Keep session lookups in Redis, not the main DB |
| **Scale the auth service** | Stateless auth servers behind a load balancer |
| **Managed identity providers** | Offload to a provider built for scale (OAuth/OIDC) |
| **Rate limiting** | Protect login endpoints from bursts and brute-force traffic |

## 7. Third-Party Service Bottlenecks

Modern apps depend on external services (**payments, cloud storage, geolocation/maps, email/SMS**), and those services limit **your** performance, reliability and scalability.

- Causes: their **availability**, **response latency**, **rate limits**, or **API changes**.
- You **can't scale them yourself**, so you must design around them.

**Example:** a **ride-sharing app** depends on an external **mapping service**. If it's slow or down, ride matching and ETAs suffer.

| Fix | How |
|---|---|
| **Timeouts** | Never wait forever on an external call |
| **Retries with backoff** | Recover from brief failures without hammering them |
| **Circuit breaker** | Stop calling a failing provider; fail fast (see [1.2.3.2 §6](../1.2.3-System-architecture/1.2.3.2-Microservices.md#6-fault-tolerance-circuit-breaker-and-friends)) |
| **Caching** | Cache results that don't change often (e.g. geocoding a fixed address) |
| **Fallbacks / multiple providers** | Degrade gracefully or switch to a backup provider |
| **Async via queue** | Send emails/SMS in the background instead of in the request |
| **Respect rate limits** | Track quotas; batch requests |

## 8. Code Execution Bottlenecks

**Inefficient algorithms, excessive CPU use, runtime overhead or poor synchronization** limit performance.

- Inefficient algorithms do **more and more work** as data grows.
- **Unnecessary processing, locking or synchronization** slows request handling.
- **Optimizing algorithms** and cutting needless computation improves performance and scalability.

**Example:** an app that repeatedly processes a large dataset with an inefficient algorithm burns CPU, and response times climb as the workload grows.

```java
// ❌ O(n²): for each order, scan the whole customer list
for (Order o : orders) {                       // 100,000 orders
    for (Customer c : customers) {             // × 100,000 customers = 10 billion checks
        if (c.id == o.customerId) { o.customer = c; break; }
    }
}

// ✅ O(n): build a lookup map once
Map<Long, Customer> byId = new HashMap<>();
for (Customer c : customers) byId.put(c.id, c);   // 100,000 inserts
for (Order o : orders) o.customer = byId.get(o.customerId);   // 100,000 lookups
```

| Fix | How |
|---|---|
| **Profile first** | Use a profiler / flame graph to find the hot code; don't guess |
| **Better algorithms & data structures** | Hash maps over nested loops; avoid repeated work |
| **Reduce lock contention** | Smaller critical sections, concurrent collections, avoid global locks |
| **Avoid blocking I/O** | Async/non-blocking calls so threads aren't stuck waiting |
| **Memoize / cache** | Don't recompute identical results |

## 9. Data Storage Bottlenecks

The **storage system can't provide enough capacity, throughput or I/O performance** for the workload.

- **High disk I/O or storage latency** slows apps that read/write often.
- **Low storage throughput** limits how fast data can be processed.
- **Limited capacity** stops the system from holding growing data.

**Example:** a cloud **file-sharing platform** gets a flood of uploads; insufficient storage throughput slows both uploads and downloads.

| Fix | How |
|---|---|
| **Faster storage** | SSD/NVMe, provisioned-IOPS volumes |
| **Object storage** | Store files/blobs in scalable object stores (e.g. S3) instead of local disks or the DB |
| **Distribute data** | Spread across many disks/nodes (partitioning, distributed file systems) |
| **Caching & CDN** | Serve hot files from memory or the edge |
| **Direct uploads** | Let clients upload straight to object storage with pre-signed URLs, bypassing app servers |
| **Data lifecycle** | Archive or tier cold data to cheaper storage; delete what's not needed |

## 10. Finding Bottlenecks

You can't fix what you can't see. A practical approach:

| Step | How |
|---|---|
| **1. Measure end-to-end** | Track latency (p95/p99), throughput and error rate per endpoint |
| **2. Trace requests** | **Distributed tracing** shows which hop (DB, auth, external API) takes the time |
| **3. Check resources (USE)** | For every resource: **U**tilization, **S**aturation (queueing), **E**rrors |
| **4. Look for queues** | Growing queues/waits (DB connection pool, thread pool, message lag) point to the bottleneck |
| **5. Load test** | Increase load until something saturates; that's the bottleneck. *(See [1.2.4.3 §5](1.2.4.3-Choosing-the-Right-Scalability-Approach.md#5-testing-your-apps-scalability).)* |
| **6. Profile** | DB `EXPLAIN` / slow-query logs; code profilers / flame graphs |
| **7. Fix, then re-measure** | Confirm the improvement; find the **next** bottleneck |

| Symptom | Likely bottleneck |
|---|---|
| DB CPU high, slow-query log full | **Database** |
| App CPU at 100%, DB idle | **Server / code** |
| Low CPU everywhere but high latency | **Network**, **locks**, or **waiting on an external service** |
| Login page slow, rest fine | **Authentication** |
| Timeouts only on payment/map features | **Third-party service** |
| High disk wait / I/O queue | **Storage** |

## 11. Quick Revision

- **Bottleneck** = the component that **restricts the whole system's** throughput; shows up under **peak load**; **fixing one exposes the next**.
- System capacity = capacity of its **slowest stage**.
- **7 types:**
  1. **Database:** slow queries, missing indexes, locks, connections → indexes, caching, replicas, pooling, sharding.
  2. **Network:** bandwidth, latency, packet loss, congestion → CDN, compression, fewer round trips, co-location.
  3. **Server:** CPU/RAM/disk limits → scale out/up, offload to queues/workers.
  4. **Authentication:** login surges, slow verification → JWT, session caching, scale auth.
  5. **Third-party:** latency, downtime, rate limits → timeouts, retries, circuit breakers, caching, fallbacks.
  6. **Code execution:** bad algorithms, CPU, locks → profile, better algorithms, less contention.
  7. **Data storage:** I/O, throughput, capacity → SSD/NVMe, object storage, distribution, CDN.
- **Find them:** measure → trace → USE (utilization, saturation, errors) → load test → profile → fix → re-measure.

## 12. Self-Check Quiz: Interview Q&A

> ⭐ These 6 questions come from the GeeksforGeeks suggested quiz and are **important for system design interviews**. Try each one before opening the answer.

### Q1. What is a bottleneck in the context of system design and scalability?

- A. A component that limits overall system performance under heavy workload
- B. A component that automatically increases system capacity
- C. A component that stores all application data
- D. A component that replaces the need for servers

<details>
<summary>Answer</summary>

**A. A component that limits overall system performance under heavy workload**

Any resource (CPU, memory, disk, network, database…) that restricts overall throughput. See [§1](#1-what-is-a-bottleneck).
</details>

### Q2. Why are database bottlenecks common in large-scale applications?

- A. Because databases often handle a large number of queries and transactions
- B. Because databases eliminate the need for caching
- C. Because databases reduce system latency automatically
- D. Because databases only work with small applications

<details>
<summary>Answer</summary>

**A. Because databases often handle a large number of queries and transactions**

Almost every request touches the DB; slow queries or poor indexing then hurt the whole system, and databases are harder to scale out than stateless servers. See [§3](#3-database-bottlenecks).
</details>

### Q3. What typically causes a network bottleneck in distributed systems?

- A. Limited bandwidth or high network latency
- B. Using too many caching layers
- C. Running applications on powerful servers
- D. Using multiple database replicas

<details>
<summary>Answer</summary>

**A. Limited bandwidth or high network latency**

Data can't move fast enough between components (also packet loss and congestion). See [§4](#4-network-bottlenecks).
</details>

### Q4. When does a server bottleneck occur in a system?

- A. When the server cannot handle more concurrent requests due to limited resources
- B. When multiple servers share the workload efficiently
- C. When caching reduces database queries
- D. When a load balancer distributes traffic evenly

<details>
<summary>Answer</summary>

**A. When the server cannot handle more concurrent requests due to limited resources**

CPU, memory or disk I/O run out as requests or processing grow. *(B, C and D are ways to **avoid** bottlenecks.)* See [§5](#5-server-bottlenecks).
</details>

### Q5. What is an authentication bottleneck in system design?

- A. When verifying user identity becomes slow due to high authentication requests
- B. When the system does not require user login
- C. When authentication removes database access
- D. When user data is stored only in cache

<details>
<summary>Answer</summary>

**A. When verifying user identity becomes slow due to high authentication requests**

The login/identity system can't process requests fast enough, e.g. an e-banking app at peak times. See [§6](#6-authentication-bottlenecks).
</details>

### Q6. How can inefficient code create a bottleneck in an application?

- A. By increasing CPU usage and slowing down execution of tasks
- B. By automatically improving database performance
- C. By reducing system memory usage
- D. By eliminating network communication

<details>
<summary>Answer</summary>

**A. By increasing CPU usage and slowing down execution of tasks**

Poor algorithms (e.g. O(n²) where O(n) is possible) consume excessive resources, and the cost grows with the workload. See [§8](#8-code-execution-bottlenecks).
</details>

### 🧠 Key Takeaways for Interviews

| # | Remember |
|---|---|
| 1 | Throughput = the **slowest stage's** throughput; scale the bottleneck, not everything |
| 2 | The **database** is the most common bottleneck: indexes, cache, replicas, pooling, shards |
| 3 | Offload heavy or external work to **queues and workers** |
| 4 | Protect against **third-party** slowness: timeouts, retries, circuit breakers, fallbacks |
| 5 | **Measure, don't guess**: tracing, USE method, load tests, profilers |
| 6 | Fixing one bottleneck **reveals the next**; it's an ongoing loop |

### Bonus Questions

> Extra practice on the rest of the topic.

### B1. You triple your app servers but throughput doesn't change. Why?

<details>
<summary>Answer</summary>

The bottleneck is **somewhere else**, often the **database** (or an external service, or locks). More capacity at a non-limiting stage adds nothing; find and fix the narrowest point.
</details>

### B2. What is the N+1 query problem?

<details>
<summary>Answer</summary>

Loading a list with **1 query**, then running **one extra query per item** (N more) to load related data, so N+1 round trips. Fix with a **JOIN**, an `IN (...)` query, or **eager loading** in the ORM.
</details>

### B3. How would you remove a CPU bottleneck caused by image processing in the request path?

<details>
<summary>Answer</summary>

Make it **asynchronous**: store the upload, put a job on a **queue**, return immediately ("processing…"), and let an **auto-scaled worker pool** resize images. App servers stay responsive.
</details>

### B4. Why can JWTs relieve an authentication bottleneck?

<details>
<summary>Answer</summary>

Services can **verify a signed token locally** on each request instead of calling a central auth service or session database every time, which removes a hotspot. Only login/refresh hits the auth service.
</details>

### B5. What does the USE method check?

<details>
<summary>Answer</summary>

For every resource (CPU, memory, disk, network, connection pools): **Utilization** (how busy), **Saturation** (how much work is queued/waiting), **Errors**. High saturation is a strong sign of a bottleneck.
</details>

### B6. Low CPU everywhere, but requests are slow. What could the bottleneck be?

<details>
<summary>Answer</summary>

Something where the system is **waiting**, not computing: **network latency**, **lock contention**, an exhausted **connection pool**, slow **disk I/O**, or a slow **third-party service**. Distributed tracing shows where the time goes.
</details>
