## 1. What is Monolithic Architecture?

A **monolithic architecture** builds the whole application as **one single unit**: one codebase, built into one deployable artifact, running as one process.

- The **user interface**, **business logic** and **data access** layers all live in the same codebase and ship together.
- It is the **traditional** way to build software, and it is popular because it is **simple to start with**.
- The opposite approach is **microservices**, where the application is split into small services that are deployed separately.
- The trade-off: as the app grows, the single unit becomes **rigid**. It gets harder to scale, change and maintain.

> 💡 **Key idea:** "Monolith" means *one deployable unit*, not *bad code*. A monolith can be well organized inside; what makes it a monolith is that everything is built, released and scaled together.

**Example: an e-commerce app.** The product catalog, user accounts, cart, orders and payments are all modules of one application. A change to the cart means rebuilding and redeploying the whole app.

## 2. Characteristics

| Characteristic | What it means |
|---|---|
| **Single codebase** | All major components are developed and kept in one repository/project. Easy to manage at the start. |
| **Tight coupling** | Components depend directly on each other, so a change in one place can ripple into others. |
| **Shared runtime** | Components run in the **same process** and talk through **direct function/method calls**, with no network hop between them. |
| **Layered structure** | Code is usually split into layers (presentation → business logic → data), but the layers are packaged and deployed together. |
| **Limited independent scaling** | You can't scale just one part. You scale the **whole application**. |
| **Single-unit deployment** | The entire app is packaged, tested and deployed as one unit. Any change means redeploying everything. |

---

## 3. Why Monoliths Still Matter

Microservices get a lot of attention, but monoliths are still the right choice in many situations:

| Reason | Why |
|---|---|
| **Simplicity** | One codebase, one build, one deployment. Easier to develop, run and understand. |
| **Cost** | Fewer servers, pipelines and moving parts. Cheaper for small and medium projects. |
| **Performance** | In-process calls are much faster than network calls between services, so there is less communication overhead. |
| **Security** | Fewer network endpoints between components means a smaller attack surface to secure. (Overall security still depends on good design and practice.) |
| **Legacy systems** | A huge number of existing systems are monoliths. You need to understand them to maintain, modernize or migrate them. |

> 💡 Many successful products **started as monoliths** and only split into services once the team and traffic grew. "Monolith first" is a common recommendation for new products.

---

## 4. Components of a Monolith

| Component | Responsibility |
|---|---|
| **User Interface (UI)** | Handles user interaction: pages, forms, buttons. |
| **Application / business logic** | The core functionality. Processes requests from the UI and applies the business rules. |
| **Data access layer** | Talks to the database: query, insert, update, delete. |
| **Database** | Stores the application's data (relational, NoSQL, or other). Usually **one shared database**. |
| **External dependencies** | Third-party APIs, authentication providers, payment gateways, message queues. |
| **Middleware** | Cross-cutting concerns: logging, security, performance monitoring, request handling. |

---

## 5. Design Principles

The goal is to keep a single codebase **manageable, consistent and simple** as it grows.

| Principle | In practice |
|---|---|
| **Modularity** | Split the code into clear modules (e.g. `catalog`, `orders`, `payments`) even though they ship together. |
| **Separation of concerns** | Keep UI, business logic and data access apart. Easier to read, test and debug. |
| **Scalability** | Design so the app can run as **many identical copies** behind a load balancer: keep it stateless, use caching and async processing. |
| **Encapsulation** | Each module exposes a small public interface and hides its internals, to limit dependencies between modules. |
| **Consistency** | Use the same coding style, patterns and conventions across the whole codebase. |

### The modular monolith

Applying these principles well gives a **modular monolith**: one deployable unit, but with **strict boundaries** between modules (each module owns its own tables and only talks to others through defined interfaces).

> 💡 A modular monolith gets most of the simplicity of a monolith **and** makes a later move to microservices much easier, because the service boundaries already exist in the code.

---

## 6. Advantages

- **Simple** to develop, test and deploy: everything is in one codebase.
- **Easier debugging**: one process, one log stream, full stack traces across modules.
- **Better performance** for small apps: no network overhead between components.
- **Simple transactions**: one database means you can use normal ACID transactions across features.
- **Lower initial cost** and **faster delivery**: ideal for MVPs and small teams.

---

## 7. Deployment Challenges

| Challenge | What goes wrong |
|---|---|
| **Long deployment cycles** | All components are packaged, tested and deployed together, so every release takes longer as the codebase grows. |
| **Risk of downtime** | A deployment touches the **whole app**. If it fails, everything can go down. Stopping the app to deploy causes downtime. *Mitigation:* **blue-green** or **rolling** deployments. |
| **Limited scalability** | You can run more copies of the whole app, but you can't scale only the busy part. |
| **Resource waste** | If only search is under load, you still have to scale catalog, payments, accounts... Unused capacity costs money. |
| **Limited flexibility** | Tight coupling means one change can affect many parts, raising the risk of bugs. It's also hard to adopt a new language or framework for just one part. |
| **Large blast radius** | A bug or memory leak in one module can crash the **entire** process. |

> 💡 **Blue-green deployment:** run the new version (green) next to the old one (blue), then switch traffic over. **Rolling deployment:** replace instances one at a time. Both avoid taking the whole app offline.

## 8. Scaling a Monolith

Monoliths are harder to scale, but there are well-known strategies:

| Strategy | How it helps |
|---|---|
| **Vertical scaling (scale up)** | Add more CPU, memory or storage to the server. Simple, but there's a hardware ceiling and cost rises fast. |
| **Horizontal scaling + load balancing (scale out)** | Run **several identical copies** of the app and spread traffic across them with a load balancer. Requires the app to be **stateless** (sessions in a shared store, not in memory). |
| **Performance optimization** | Profile to find bottlenecks: slow queries, poor algorithms, wasted resources. |
| **Caching** | Keep frequently used data in memory (e.g. Redis) to reduce load on the database and external services, and speed up responses. |
| **Database read replicas** | Send reads to replicas and writes to the primary. Useful for read-heavy apps. |
| **Database sharding** | If the database is the bottleneck, split the data across several database instances (shards), each holding part of it. |
| **Async processing** | Push slow work (emails, reports) onto a queue handled by background workers. |

```
Vertical:   [ small server ]  ──►  [   BIG SERVER   ]

Horizontal:              ┌─► [ App copy 1 ] ─┐
            Users ─► LB ─┼─► [ App copy 2 ] ─┼─► Cache ─► DB (primary + replicas)
                         └─► [ App copy 3 ] ─┘
```

## 9. Monolith vs Microservices

| Aspect | Monolith | Microservices |
|---|---|---|
| **Codebase** | One | Many (one per service) |
| **Deployment** | Whole app at once | Each service independently |
| **Scaling** | Whole app | Each service on its own |
| **Communication** | In-process function calls | Network calls (HTTP/gRPC, messaging) |
| **Database** | Usually one shared DB | Usually one DB per service |
| **Transactions** | Simple ACID transactions | Distributed (sagas, eventual consistency) |
| **Debugging** | Easier: one process | Harder: needs tracing across services |
| **Failure impact** | One bug can take down everything | Failures can be isolated to one service |
| **Tech stack** | One stack for everything | Each service can choose its own |
| **Operational cost** | Low | High (service discovery, monitoring, CI/CD per service) |
| **Best for** | Small teams, MVPs, simple domains | Large teams, complex domains, uneven scaling needs |

> 📖 **Deep dive:** [1.2.3.3 Monolithic vs Microservices Architecture](1.2.3.3-Monolithic-vs-Microservices.md)

### When to choose a monolith

- New product or MVP where **speed of delivery** matters most.
- **Small team** (one team can understand the whole codebase).
- Domain is **not yet well understood**, so service boundaries would be guesses.
- Load is modest or **scales evenly** across features.

## 10. Migrating from a Monolith to Microservices

Migration is complex and should be gradual and planned. Common strategies:

| Strategy | How it works |
|---|---|
| **Strangler Fig pattern** | Put a routing layer in front of the monolith. Build new features as services, and move existing features out **one at a time**, redirecting their traffic. The monolith "shrinks" until it can be retired, with no big-bang rewrite. |
| **Decompose by business capability** | Draw service boundaries around business domains (orders, payments, inventory), so each team owns one area. |
| **Database decoupling** | Give each service its **own database/schema** so services can be developed and deployed independently. Often the hardest step. |
| **Event-driven communication** | Services talk through **events** on a message broker instead of direct calls. Reduces coupling and improves resilience and scalability. |

```
Strangler Fig, step by step:

  Step 1:  Users ─► Router ─► [ MONOLITH: catalog, cart, orders, payments ]

  Step 2:  Users ─► Router ─┬─► [ Payments service ]
                            └─► [ MONOLITH: catalog, cart, orders ]

  Step 3:  Users ─► Router ─┬─► [ Payments ] [ Orders ] [ Cart ]
                            └─► [ MONOLITH: catalog ]

  Step 4:  Monolith retired: every feature is its own service
```

> ⚠️ Don't migrate just because microservices are fashionable. Split only when the monolith's pain (slow releases, scaling limits, team conflicts) is real.

---

## 11. Quick Revision

- **Monolith** = whole app built, deployed and scaled as **one unit** (one codebase, one process, usually one DB).
- **6 characteristics:** single codebase · tight coupling · shared runtime · layered structure · limited independent scaling · single-unit deployment.
- **Components:** UI · business logic · data access layer · database · external dependencies · middleware.
- **Design principles:** modularity · separation of concerns · scalability · encapsulation · consistency → a **modular monolith**.
- **Pros:** simple, cheap, fast in-process calls, easy debugging, simple transactions, great for MVPs.
- **Cons:** long deployments, downtime risk, scale-everything-or-nothing, wasted resources, tight coupling, large blast radius.
- **Scaling:** vertical · horizontal + load balancer · optimization · caching · read replicas · sharding · async queues.
- **Migration:** Strangler Fig · decompose by business capability · database per service · event-driven communication.

## 12. Self-Check Quiz: Interview Q&A

> ⭐ These 6 questions come from the GeeksforGeeks suggested quiz and are **important for system design interviews**. Try each one before opening the answer.

### Q1. In a monolithic architecture, what does the term "single codebase" primarily indicate?

- A. All application components are developed and maintained in one unified code repository
- B. Each service is stored in a separate repository
- C. The database and UI are hosted on different platforms
- D. Only the business logic is stored in a single repository

<details>
<summary>Answer</summary>

**A. All application components are developed and maintained in one unified code repository**

In a monolith, the UI, business logic and data access layers are part of the same codebase and are built and deployed together as one application. *(B describes microservices; D is wrong because **every** layer is in the one codebase, not just the business logic.)* See [§2 Characteristics](#2-characteristics).
</details>

### Q2. Why is scaling a monolithic architecture often considered inefficient?

- A. Because each component can be scaled independently
- B. Because the entire application must be replicated even if only one part needs scaling
- C. Because the database cannot handle large data
- D. Because monolithic systems cannot run on multiple servers

<details>
<summary>Answer</summary>

**B. Because the entire application must be replicated even if only one part needs scaling**

The components are tightly integrated, so scaling usually means duplicating the whole system rather than just the busy component. *(A is the opposite: that's a microservices benefit. D is false: monoliths **can** run on many servers behind a load balancer, it's just wasteful.)* See [§8 Scaling a Monolith](#8-scaling-a-monolith).
</details>

### Q3. Which component in a monolithic architecture is responsible for handling interactions with the database?

- A. User Interface layer
- B. Application Logic layer
- C. Middleware
- D. Data Access Layer

<details>
<summary>Answer</summary>

**D. Data Access Layer**

The Data Access Layer manages communication with the database and performs operations such as querying, inserting, updating and deleting data. See [§4 Components](#4-components-of-a-monolith).
</details>

### Q4. Which design principle in monolithic architecture helps organize code into separate modules while keeping a single codebase?

- A. Modularity
- B. Event-driven design
- C. Event-driven communication
- D. Service decomposition

<details>
<summary>Answer</summary>

**A. Modularity**

Modularity divides the application into logical modules within the same codebase, making the system easier to manage and maintain. *(B, C and D are about splitting into separate services, i.e. microservices.)* See [§5 Design Principles](#5-design-principles).
</details>

### Q5. What is the primary purpose of using caching in a monolithic system?

- A. To increase the number of servers automatically
- B. To reduce load on the application and external services by storing frequently accessed data
- C. To replace the main database
- D. To allow independent service deployment

<details>
<summary>Answer</summary>

**B. To reduce load on the application and external services by storing frequently accessed data**

Caching keeps frequently used data in fast storage temporarily, so the system doesn't keep asking the database or other services for the same information. *(A is auto-scaling; a cache works **alongside** the database, it doesn't replace it.)* See [§8 Scaling a Monolith](#8-scaling-a-monolith).
</details>

### Q6. Which migration strategy gradually replaces parts of a monolithic application with microservices without shutting down the system?

- A. Vertical scaling strategy
- B. Strangler Fig Pattern
- C. Database replication
- D. Load balancing

<details>
<summary>Answer</summary>

**B. Strangler Fig Pattern**

The Strangler Fig Pattern replaces parts of the monolith with microservices step by step, so the original system keeps running during the migration. See [§10 Migration](#10-migrating-from-a-monolith-to-microservices).
</details>

### 🧠 Key Takeaways for Interviews

| # | Remember |
|---|---|
| 1 | Monolith = **one unit** to build, deploy and scale |
| 2 | Strengths: **simplicity, low cost, fast in-process calls, easy transactions** |
| 3 | Weaknesses: **all-or-nothing scaling and deployments, tight coupling, big blast radius** |
| 4 | Scale it with **load balancing + stateless copies, caching, replicas, sharding** |
| 5 | Keep it **modular** so it can be split later |
| 6 | Migrate gradually with the **Strangler Fig** pattern, not a big-bang rewrite |

### Bonus Questions

> Extra practice on the rest of the topic.

### B1. What defines a monolithic architecture?

- A. Each feature is deployed as a separate service
- B. All components are built and deployed as a single unit
- C. Every component has its own database
- D. Components communicate only through events

<details>
<summary>Answer</summary>

**B.** A monolith packages UI, business logic and data access into one deployable unit. A, C and D describe microservices.
</details>

### B2. How do components inside a monolith usually communicate?

- A. HTTP requests over the network
- B. A message broker
- C. Direct function or method calls in the same process
- D. gRPC

<details>
<summary>Answer</summary>

**C.** They share one runtime, so they call each other directly. This is why monoliths avoid network overhead between components.
</details>

### B3. Only the search feature of your monolith is overloaded. What is the problem when scaling?

<details>
<summary>Answer</summary>

You can't scale **just search**. You have to run more copies of the **whole application**, which wastes resources on the parts that aren't busy. That's the "limited independent scalability" drawback.
</details>

### B4. Which deployment strategies reduce downtime when releasing a monolith?

<details>
<summary>Answer</summary>

**Blue-green deployment** (run the new version beside the old one, then switch traffic) and **rolling deployment** (replace instances one by one).
</details>

### B5. What is the difference between vertical and horizontal scaling of a monolith?

<details>
<summary>Answer</summary>

**Vertical** = make one server bigger (more CPU/RAM); simple but limited by hardware. **Horizontal** = run more copies of the app behind a load balancer; needs the app to be stateless.
</details>

### B6. What is a modular monolith, and why is it useful?

<details>
<summary>Answer</summary>

A single deployable app whose code is split into **modules with strict boundaries** (own data, defined interfaces). It keeps the simplicity of a monolith and makes a future split into microservices much easier.
</details>

### B7. A 4-person startup is building an MVP and isn't sure how the domain will evolve. Monolith or microservices?

<details>
<summary>Answer</summary>

**Monolith** (ideally modular). It's faster to build, cheaper to run, and service boundaries would be guesses at this stage. Split later if real scaling or team problems appear.
</details>
