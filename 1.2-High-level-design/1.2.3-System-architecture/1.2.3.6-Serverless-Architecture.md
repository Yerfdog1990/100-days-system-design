## 1. What is Serverless Architecture?

**Serverless architecture** is a cloud model where the **cloud provider manages the infrastructure** (provisioning servers, scaling, patching, maintenance) and **developers just write and deploy code**.

- Code runs **automatically in response to events or requests**.
- The provider handles **server management, scaling and resource allocation**.
- You typically **pay only for what you use** (number of invocations and execution time), not for idle servers.

> 💡 **Key idea:** "Serverless" doesn't mean *no servers*. The servers are still there, you just **don't see or manage them**. Your unit of deployment is a **function**, not a machine.

**Example:** a user uploads an image → a serverless function **automatically** resizes it → the result is saved to storage. No one provisioned or patched a server.

### Two flavours of serverless

| Flavour | What it is | Examples |
|---|---|---|
| **FaaS** (Functions as a Service) | You write small **functions**; the platform runs them on events | AWS Lambda, Azure Functions, Google Cloud Run functions |
| **BaaS** (Backend as a Service) | Fully **managed backend services** you use without running servers | Managed databases (DynamoDB, Firestore), object storage (S3), auth services |

A serverless application usually combines both: **functions** for business logic, **managed services** for data, files and identity.

## 2. How a Serverless Application Fits Together

```
                          ┌──────────┐
                          │ Web App  │
                          └────┬─────┘
                               │ HTTPS request
                               ▼
                       ┌───────────────┐      ┌────────────┐
                       │  API Gateway  │◄────►│ Authorizer │  "who are you? are you allowed?"
                       │ route·validate│      └────────────┘
                       │ throttle·auth │
                       └───────┬───────┘
                               ▼
                 ┌─────────────────────────────┐
                 │   SERVERLESS FUNCTIONS      │  business logic, no servers to manage
                 │  createOrder  getProfile …  │
                 └──┬──────────┬──────────┬────┘
                    ▼          ▼          ▼
              ┌──────────┐ ┌─────────┐ ┌──────────────┐
              │ Database │ │ Storage │ │ External APIs│      MANAGED SERVICES
              └──────────┘ └─────────┘ └──────────────┘

  Event-driven triggers (no API Gateway needed):
     message queue ─┐
     event stream  ─┼──► function runs automatically
     file uploaded ─┘
```

| Component | Role |
|---|---|
| **Web app** | Sends requests to the application through the API Gateway. |
| **API Gateway** | The **entry point**: routes requests, validates them, **throttles** traffic, and handles authentication/authorization when needed. |
| **Authorizer** | Checks the client's **identity and permissions** before the request goes further. |
| **Serverless functions** | Run the **business logic**. |
| **Managed services** | **Database** (store/retrieve data), **storage** (files, images, documents), **external APIs** (third-party services). |
| **Event-driven triggers** | **Queues, event streams or object storage** can trigger functions **directly**, with no HTTP request involved. |

## 3. How a Function Runs: Events, Instances and Cold Starts

### Triggered by events

A function **doesn't run continuously**. It runs **when an event happens**:

| Trigger | Example |
|---|---|
| **HTTP request** | `POST /orders` via API Gateway |
| **File upload** | New image in a storage bucket |
| **Database change** | A row inserted or updated |
| **Message / stream** | A message on a queue, a record on an event stream |
| **Schedule** | Every night at 02:00 (cron) |

This makes serverless **naturally event-driven** (see [1.2.3.4 Event-Driven Architecture](1.2.3.4-Event-Driven-Architecture.md)).

### A minimal function

```python
# AWS Lambda-style handler (Python): resize an uploaded image
import boto3                                   # runs once per instance (init phase)
s3 = boto3.client("s3")                        # reused across warm invocations

def handler(event, context):                   # runs once per event
    record = event["Records"][0]["s3"]
    bucket = record["bucket"]["name"]
    key    = record["object"]["key"]
    # ... download, resize, upload thumbnail ...
    return {"status": "ok", "thumbnail": f"thumbs/{key}"}
```

> 💡 Code **outside** the handler (imports, clients, connections) runs once when an instance starts and is **reused** while that instance stays warm. Code **inside** runs on every event.

### Stateless by design

Function instances are **short-lived** and can be created or destroyed at any time, and two requests from the same user may hit **different** instances. So functions are **stateless**: anything that must survive goes to **external services** (database, cache, storage).

### Instance lifecycle: cold vs warm start

```
 event arrives
     │
     ├── a warm instance is free? ── YES ──► run handler                    (WARM START: fast)
     │
     └── NO ──► create execution environment ─► load code ─► run init code ─► run handler
                └──────────────── extra latency ─────────────────┘           (COLD START)

 after the request: the instance stays warm for a while, then is shut down if idle
```

- **Cold start:** the platform must **initialize a new instance** (after idleness or when scaling up), which adds latency.
- **Warm start:** an existing instance is reused, so it's fast.

## 5. Serverless Design Patterns

### 5.1 API Gateway pattern

The **API Gateway** is the entry point for client requests and routes them to functions or other backends.

- Handles HTTP requests: **authentication, authorization, validation, routing**.
- Adds **rate limiting, monitoring** and request management.

```
 Client ─► API Gateway ─┬─► GET  /users/{id}  ─► getUser()
                        ├─► POST /orders      ─► createOrder()
                        └─► GET  /orders/{id} ─► getOrder()
```

### 5.2 Event stream processing

Functions process events from **streams**: application logs, financial transactions, IoT devices, social media feeds.

- Each batch of events **triggers** a function that processes data **incrementally**.
- Good for **real-time analytics, monitoring and alerts**.

```
 IoT sensors ─► event stream ─► function (per batch) ─► "temp > 80°C" ─► alert
                                       └──────────────► metrics DB ─► dashboard
```

### 5.3 Aggregator

One function **calls several services/functions** and **combines** their responses into **one response** for the client.

```
                    ┌─► profile service ─┐
 Client ─► aggregator ─► orders service ─┼─► one combined JSON
                    └─► reviews service ─┘
```

This simplifies the client: **one call** instead of three.

### 5.4 Strangler Fig pattern

Gradually **replace a legacy system** by moving features into new components, **including serverless functions**, one at a time, with no big rewrite. *(See [1.2.3.1 Monolithic Architecture §10](1.2.3.1-Monolithic-Architecture.md#10-migrating-from-a-monolith-to-microservices).)*

### 5.5 Circuit Breaker

Stops **repeated calls to a failing service**, preventing **cascading failures**.

- **Opens** after a set number of failures.
- **Temporarily blocks** further calls.
- Lets the system **recover** and keep working in a **degraded** mode if appropriate.

*(See [1.2.3.2 Microservices §6](1.2.3.2-Microservices.md#6-fault-tolerance-circuit-breaker-and-friends) for the closed/open/half-open states.)*

## 6. Scaling and Performance

### 6.1 Scaling

| Concept | Meaning |
|---|---|
| **Automatic scaling** | The platform **adds instances** as requests/events grow and **removes them** as they drop, within the provider's **limits and configuration**. Often scales to **zero** when idle. |
| **Cold starts** | Each new instance must initialize, so scaling up (or waking from idle) adds **latency**. |
| **Throttling** | Providers cap invocations/concurrency. Above the limit, requests are **throttled** (rejected or delayed). |

### 6.2 Performance optimization

| Strategy | How |
|---|---|
| **Lean function code** | Keep functions small and focused; use **async** programming where it helps. |
| **Manage dependencies** | Remove unused libraries and files: **smaller packages start faster**. |
| **Reuse connections** | Create DB/HTTP clients **outside the handler** so warm invocations reuse them. Configure **connection limits and pooling** to suit the platform; thousands of instances can **exhaust a database's connections**. |
| **Reduce cold starts** | Keep init work small; use the provider's **pre-warmed / provisioned capacity** feature for latency-sensitive paths (at extra cost). |
| **Right-size memory** | On many platforms CPU scales with memory, so more memory can make a function **faster and sometimes cheaper**. |

## 7. Security Best Practices

| # | Practice | Why / how |
|---|---|---|
| 1 | **Least privilege** | Give **each function only the permissions it needs** (e.g. `resizeImage` can read one bucket and write another, nothing else). If it's compromised, the damage is limited. |
| 2 | **Secure secrets** | **Never hard-code** API keys, tokens or passwords. Use a managed **secret manager**. |
| 3 | **Input validation** | Validate and sanitize all input, especially user data, to help prevent **SQL injection, XSS, command injection**. |
| 4 | **Secure the API Gateway** | Authenticate with **OAuth, API keys or IAM**; enable **rate limiting** and proper **CORS** policies. |
| 5 | **Encryption** | Encrypt **in transit** (HTTPS, encrypted DB connections) and **at rest** (storage and databases). |

> 💡 In serverless, **every function is its own attack surface** with its own permissions. Many small, tightly scoped roles are safer than one broad role shared by all functions.

## 8. Use Cases

| Use case | Why serverless fits |
|---|---|
| **Chatbots & virtual assistants** | Respond to messages/voice requests; **scale automatically** with user demand. |
| **Real-time data processing** | Process streams for **analytics, monitoring, alerts** without dedicated servers. |
| **Web & mobile backends** | Scalable APIs for **auth, requests and database operations**. |
| **Scheduled tasks / cron jobs** | **Backups, reports, data sync, maintenance** that run on a schedule and are idle the rest of the time. |
| **File processing** | Image resizing, video thumbnails, document conversion **on upload**. |

> 💡 Serverless shines for **spiky, unpredictable or infrequent** workloads: you pay nothing while idle and it scales up on demand.

## 9. Challenges

| Challenge | Detail | Mitigation |
|---|---|---|
| **Cold start latency** | A new execution environment must start before the request runs. | Small packages, light init, pre-warmed/provisioned capacity |
| **Execution & resource limits** | Limits on **run time, memory, concurrency, payload size**. A long video encode may exceed the max run time (e.g. AWS Lambda currently caps a run at 15 min). | Split work into steps, use workflows/queues, or containers for long jobs |
| **Debugging & monitoring** | Logic is spread across **many functions and managed services**. | Centralized logs, **distributed tracing**, correlation IDs |
| **State management** | Functions are stateless, so state must live in **external** DBs, storage or caches. | Design for external state from the start |
| **Security & compliance** | Many functions = many **permissions, secrets, network rules** to get right. | Least privilege, secret managers, policy reviews |
| **Vendor lock-in** | Triggers, permissions and managed services are **provider-specific**. | Keep business logic separate from provider glue code |
| **Cost at steady high load** | Pay-per-use is cheap when idle but can cost **more** than always-on servers for constant heavy traffic. | Compare against containers/VMs for steady workloads |

## 10. Serverless vs Servers vs Containers

| Aspect | Traditional servers / VMs | Containers (e.g. Kubernetes) | Serverless (FaaS) |
|---|---|---|---|
| **You manage** | OS, runtime, scaling, patching | Images, orchestration, scaling rules | **Just the code** (+ config) |
| **Unit of deployment** | Whole app on a machine | Container | **Function** |
| **Scaling** | Manual or auto-scaling groups | Orchestrator scales pods | **Automatic**, per event, to zero |
| **Billing** | Pay while running (even idle) | Pay for nodes (even idle) | **Pay per invocation + run time** |
| **Startup** | Minutes | Seconds | Milliseconds to seconds (**cold starts**) |
| **Long-running work** | ✅ | ✅ | ❌ limited run time |
| **State** | Can keep in memory | Usually external | **Must** be external |
| **Best for** | Legacy, full control | Steady services, portability | **Event-driven, spiky, short tasks** |

## 11. Quick Revision

- **Serverless** = the provider manages servers, scaling and maintenance; developers **write code**; **pay per use**. Servers still exist, you just don't manage them.
- **FaaS** (functions) + **BaaS** (managed DB, storage, auth).
- **Architecture:** web app → **API Gateway** (route, validate, throttle, auth) → **authorizer** → **functions** → **managed services** (DB, storage, external APIs). Queues, streams and storage can trigger functions directly.
- **Triggers:** HTTP requests, file uploads, DB changes, messages/streams, schedules → serverless is **event-driven**.
- **Stateless** functions: state lives in external services.
- **Cold start** = latency when a new instance initializes; **warm start** reuses one.
- **Providers:** AWS Lambda · Azure Functions · Google Cloud Run functions · OCI Functions.
- **Patterns:** API Gateway · event stream processing · aggregator · Strangler Fig · circuit breaker.
- **Performance:** auto-scaling, cold starts, throttling → lean code, small packages, reuse connections.
- **Security:** least privilege · secret managers · input validation · secure API Gateway · encryption in transit and at rest.
- **Use cases:** chatbots, real-time processing, web/mobile backends, cron jobs, file processing.
- **Challenges:** cold starts, execution limits, debugging, state, security/compliance, lock-in, cost at steady high load.

## 12. Self-Check Quiz: Interview Q&A

> ⭐ These 6 questions come from the GeeksforGeeks suggested quiz and are **important for system design interviews**. Try each one before opening the answer.

### Q1. What is the primary idea behind serverless architecture in cloud computing?

- A. Developers manually manage servers and infrastructure
- B. Cloud providers manage servers while developers focus on writing code
- C. Applications must run on physical servers owned by developers
- D. All applications run without using any cloud resources

<details>
<summary>Answer</summary>

**B. Cloud providers manage servers while developers focus on writing code**

The provider handles provisioning, scaling and maintenance, so developers only focus on application code. *(D is a common misconception: servers and cloud resources still exist, you just don't manage them.)* See [§1](#1-what-is-serverless-architecture).
</details>

### Q2. What triggers the execution of code in a serverless architecture?

- A. Manual server configuration by administrators
- B. Scheduled hardware operations
- C. Events such as HTTP requests, file uploads, or database changes
- D. Continuous execution of background processes

<details>
<summary>Answer</summary>

**C. Events such as HTTP requests, file uploads, or database changes**

Functions run **in response to events**, which makes serverless naturally event-driven and efficient for changing workloads. *(D is wrong: functions don't run continuously; they're idle until triggered.)* See [§3](#3-how-a-function-runs-events-instances-and-cold-starts).
</details>

### Q3. Which platform is widely known for executing serverless functions in response to cloud events?

- A. AWS Lambda
- B. Docker Engine
- C. Apache Tomcat
- D. Kubernetes Dashboard

<details>
<summary>Answer</summary>

**A. AWS Lambda**

One of the most popular serverless platforms: runs code without managing servers and integrates with many AWS services. *(Docker runs containers, Tomcat is a Java application server, and the Kubernetes Dashboard is a cluster UI.)* See [§4](#4-providers-and-platforms).
</details>

### Q4. Why are serverless functions typically designed to be stateless?

- A. Because they store all data internally
- B. Because they rely on external services for storing application state
- C. Because they cannot interact with databases
- D. Because stateless systems cannot scale

<details>
<summary>Answer</summary>

**B. Because they rely on external services for storing application state**

Instances are short-lived and can be created or destroyed at any time, so persistent data goes to databases, storage or caches. *(C is false: functions talk to databases all the time. D is backwards: statelessness is what makes them **easy** to scale.)*
</details>

### Q5. What is a major performance concern associated with serverless computing?

- A. Limited network connectivity
- B. Cold start latency when a new function instance is initialized
- C. Lack of programming language support
- D. Manual server scaling requirements

<details>
<summary>Answer</summary>

**B. Cold start latency when a new function instance is initialized**

When no warm instance is available, the platform must create an environment, load the code and run initialization first, which adds latency. *(D is wrong: scaling is automatic.)* See [§3](#3-how-a-function-runs-events-instances-and-cold-starts) and [§6](#6-scaling-and-performance).
</details>

### Q6. Why is the principle of least privilege important in serverless security?

- A. To ensure functions have unlimited access to resources
- B. To grant each function only the permissions required for its task
- C. To allow direct database access from all functions
- D. To eliminate the need for authentication

<details>
<summary>Answer</summary>

**B. To grant each function only the permissions required for its task**

If a function is compromised, the attacker can only do what that function was allowed to do, which limits the damage. See [§7](#7-security-best-practices).
</details>

### 🧠 Key Takeaways for Interviews

| # | Remember |
|---|---|
| 1 | Serverless = **no server management + auto-scaling + pay per use**; servers still exist |
| 2 | Functions are **event-triggered, short-lived and stateless**; state lives in managed services |
| 3 | Typical shape: **API Gateway → authorizer → functions → managed DB/storage/APIs** |
| 4 | Main performance issue: **cold starts**; also **throttling** and **execution limits** |
| 5 | Security: **least privilege per function**, secret managers, input validation, encryption |
| 6 | Great for **spiky, event-driven, short** tasks; weaker for **long-running or steady heavy** workloads |

### Bonus Questions

> Extra practice on the rest of the topic.

### B1. What's the difference between FaaS and BaaS?

<details>
<summary>Answer</summary>

**FaaS** runs **your code** as functions on events (Lambda, Azure Functions). **BaaS** gives you **ready-made managed backend services** (databases, storage, auth) that you use without running servers.
</details>

### B2. Why should database clients be created outside the function handler?

<details>
<summary>Answer</summary>

Code outside the handler runs **once per instance** and is **reused across warm invocations**, so you avoid opening a new connection on every request. Still configure connection limits/pooling: many instances can exhaust the database's connections.
</details>

### B3. What does the aggregator pattern do?

<details>
<summary>Answer</summary>

One function calls **several services**, **combines** their results and returns **one response**, so the client makes a single call instead of many.
</details>

### B4. Your API gets a sudden traffic spike and some requests fail with "too many requests". What's happening?

<details>
<summary>Answer</summary>

**Throttling.** The provider (or your configured concurrency limit) caps how many invocations can run at once. Requests above the limit are rejected or delayed. Raise the limit, add a queue to buffer work, or rate-limit at the API Gateway.
</details>

### B5. Name three ways to reduce cold start impact.

<details>
<summary>Answer</summary>

Any three of: keep the **deployment package small** (remove unused dependencies); keep **initialization code light**; choose a **fast-starting runtime**; use the provider's **pre-warmed/provisioned capacity** for latency-critical functions; right-size **memory**.
</details>

### B6. Would you run a 2-hour video encoding job as a single serverless function? Why or why not?

<details>
<summary>Answer</summary>

**No.** Function platforms have **maximum execution times** (e.g. 15 min on AWS Lambda), so it would be cut off. Split it into smaller steps (chunks + a workflow/queue) or run it on **containers/VMs** that support long-running work.
</details>

### B7. When can serverless be more expensive than running servers?

<details>
<summary>Answer</summary>

With **steady, high, constant traffic**. Pay-per-invocation adds up, while an always-busy server or container would be fully used anyway. Serverless is cheapest for **spiky or low/idle** workloads.
</details>
