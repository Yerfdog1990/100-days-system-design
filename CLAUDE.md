# Project instructions

## KAREF Ugenya SACCO: keep Jira and Confluence in sync

Whenever you change the KAREF requirements here (`KAREF-Ugenya-SACCO/01-Product-Requirements-SRS.md`), **always apply the same change to Jira and Confluence in the same session**:

- **Atlassian site:** https://gouma308.atlassian.net (cloudId `a1bd4f0b-1747-400b-ab4a-79c229d350a0`)
- **Confluence:** page "KAREF Ugenya SACCO" (id `131095`, space `MFS`). Mirror every edit: as-is/vision text, requirement table rows (with the Jira link in the Jira Issue column), business rules, open questions.
- **Jira:** project `KAN`. New requirement → new issue under the matching epic (A1–A8 = KAN-1..KAN-8, B Non-functional = KAN-9, C Extended = KAN-10). FR = Story, NFR/EXT = Task. Priority: Must = Highest, Should = Medium, Could = Low. Labels: `srs`, `functional`/`non-functional`/`operational`, `must`/`should`/`could`. Changed requirement → edit the existing issue's summary/description.
- **Local files:** put the new Jira key in the SRS Jira Issue column, and append the issue to `KAREF-Ugenya-SACCO/KUS-jira-import.csv` (Issue Id = Jira key number, Parent = epic number).
- **Data requirements:** `KAREF-Ugenya-SACCO/02-Data-Requirements.md` mirrors the Confluence child page "KAREF Ugenya SACCO: Data Requirements" (id `1802251`). When a requirement change adds, removes, or changes stored data, update both. The database design task is KAN-103 (milestone M2).
- **Jira issue format (agreed 2026-10-10):** keep the Jira summary as "FR-xx: short title". Epic descriptions use an **Epic Overview**: Key/Title ("Epic #N: Name", #1–#8 = A1–A8, #9 = NFR, #10 = EXT), Parent ("KAREF Digital SACCO Platform (v1)"), Epic Description. Story/task descriptions contain only three bullets: **Summary** ("As a …, I want …, so that …"), **Parent** ("Epic #N: Name"), and **Acceptance Criteria** numbered i., ii., iii. (no heading, no "Description" label, no footer). Write them with `contentFormat: html` (markdown turns the roman numerals into plain text). Requirement importance and deferral notes live in the SRS, the Jira priority, and the `wont` label. **Sub-tasks (agreed 2026-10-10):** every v1 story (not `wont`) has Jira Subtask issues broken down by acceptance criterion, ~2–3 per criterion, summary "N.M (Discipline): task" (N = criterion number, e.g. "1.1 (Backend): …"), description "**Acceptance Criterion (i):** …", and one discipline label (frontend, admin-portal, backend, qa, security, architecture, data, configuration, devops, documentation). When a story's criteria change, add/update its sub-tasks and mirror them in `KAREF-Ugenya-SACCO/04-Jira-Sub-Tasks.md`. **Story points (agreed 2026-10-10):** every story/task has a Fibonacci estimate (1, 2, 3, 5, 8, 13) weighing effort, complexity, risk and uncertainty, recorded in `KAREF-Ugenya-SACCO/05-Story-Points.md` and in Jira's "Story point estimate" field (customfield_10016). Estimate any new story the same way. **Releases (agreed 2026-10-10):** every story/task has a Jira fix version: v1.0 – AGM Go-Live (id 10003, 4 Jan → 30 Apr 2027), v1.1 – Stabilisation (10004, May–Jun 2027), v1.2 – December Dividend Payout (10005, by 10 Dec 2027), v2.0 – Future Phase (10006, deferred/`wont`). Assign new stories to a release, and mirror changes in `KAREF-Ugenya-SACCO/06-Release-Plan.md` and Confluence page 1343495. **Sprints (agreed 2026-10-10):** 14 two-week sprints on board 1 (sprint ids 4–17): Sprints 1–8 = v1.0 (4 Jan → 23 Apr 2027, ~37 pts each), 9–12 = v1.1 (May–Jun 2027), 13–14 = v1.2 (Nov 2027). Put new stories in a sprint of their release and mirror the sprint table in `06-Release-Plan.md` and Confluence page 1343495. Mirror every new or changed story in `KAREF-Ugenya-SACCO/03-Epics-and-User-Stories.md`; the Confluence page "KAREF Ugenya SACCO: Epics and User Stories" (id `1671221`) lists issues live from Jira.
